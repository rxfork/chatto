<Aside type="caution">
  Use this deployment for a test environment or a small server that can accept
  short downtime. For most production servers, use [Docker
  Compose](/guides/deployment/docker-compose/) or a different container
  runtime.
</Aside>

The standalone binary includes embedded NATS and optional automatic TLS. It
does not use an external database.

You can use the automatic TLS function in Chatto. You can also put Chatto
behind your reverse proxy.

## Architecture

<ArchDiagram />

By default, `chatto run` starts an embedded NATS server with JetStream. Chatto
reads `chatto.toml` from the current working directory. It stores embedded NATS
data in `./data/` by default.

<Aside type="caution">
  Do not start more than one Chatto server process with one embedded data
  directory. Use external NATS for a deployment with multiple processes.
</Aside>

## Prerequisites

Prepare these items:

- A Linux, macOS, or FreeBSD host with Chatto installed.
- A domain that points to the host, such as `chat.example.com`.
- Persistent storage for the Chatto data directory.
- Inbound TCP ports 80 and 443 when Chatto terminates TLS.

Install Chatto with Homebrew on macOS or Linux:

```bash
brew install chattocorp/tap/chatto
```

You can also download an archive from [GitHub
Releases](https://github.com/chattocorp/chatto/releases).

## Configure Chatto

Use the [Quick Start](/getting-started/quick-start/) guide to generate
`chatto.toml`.

Before you use the configuration in production, do these steps:

- Set `webserver.url` to the public URL.
- Create the first owner through the setup wizard or the Operator CLI. You can
  also use `owners.emails` when email is enabled.
- Configure SMTP (the default transport) or JMAP if Chatto must send
  registration or verification email.
- Select automatic Chatto TLS or TLS in a reverse proxy.
- Put `nats.embedded.data_dir` on persistent storage.
- Set `nats.embedded.sync_interval` to `always` for the strongest protection
  against data loss when the host stops without a normal shutdown.
- Select the permitted login methods.
- Do a test of an external login provider before you set `auth.direct_login`
  to `false`.

Examine these optional sections for the specified features:

- Use `[core.assets.s3]` for S3-compatible upload storage.
- Use `[push]` for push notifications.
- Use `[video]` and `[asset_processing]` for video uploads.
- Use `[livekit]` for calls.

For a single embedded NATS server, use this setting:

```toml
[nats.embedded]
sync_interval = 'always'
```

This setting syncs each JetStream write to disk before NATS acknowledges it.
It reduces write throughput. If you omit it, Chatto keeps the NATS default sync
interval.

## Email-Free Deployment

Generate a configuration with `chatto init`. Edit these sections in
`chatto.toml`; do not add a second copy of an existing section:

```toml
[email]
disabled = true

[auth]
direct_registration = true
direct_login = true
account_creation_policy = 'open'

[operator_api]
enabled = true
socket_path = './data/operator.sock'
```

Keep the generated secrets and embedded NATS settings. Set `webserver.url`
to your server URL. No SMTP or JMAP settings are required. Chatto keeps the
bundled frontend and embedded NATS in the same binary. Automatic TLS can also
run without a contact email in this mode.

Start the server:

```sh
chatto run -c chatto.toml
```

On a new server, open the setup wizard to create the first owner with a
username and password. The wizard does not ask for email. To create the first
owner from a terminal instead, run this command in a second terminal from the
same directory. Enter the password at the prompt:

```sh
chatto operator --operator-socket ./data/operator.sock user create --login firstowner --role owner
```

An operator-created account closes the first-run wizard. Do not create an
ordinary account first if you intend to use the wizard. Owner access uses the
existing owner role. To give an existing account owner access, use its stable
user ID from `user list`:

```sh
chatto operator --operator-socket ./data/operator.sock user list
chatto operator --operator-socket ./data/operator.sock user role add USER_ID owner
```

The operator socket is local and gives full server control. Keep its directory
private and its default `0600` permissions. See [Operator
CLI](/guides/operations/operator-cli/) for access and automation instructions.

Users register with a unique username and password. Set
`auth.account_creation_policy = 'invite_only'` to require an existing invite
link. Create links through the existing invitation controls. Expiration,
revocation, and use limits still apply. Open registration does not use an
invitation. Set `auth.direct_registration = false` to close public signup.

Users sign in with their username and password. Email fields, verification,
email management, and email password recovery are unavailable. Users can still
change their password in authenticated account settings. For a lost password,
the operator confirms the user's identity through a trusted channel, then runs:

```sh
chatto operator --operator-socket ./data/operator.sock user list
chatto operator --operator-socket ./data/operator.sock user set-password USER_ID
```

Enter the new password at the prompt. The reset invalidates older sessions.
Share the new password through a secure channel.

Restart Chatto after changing `email.disabled`. Existing usernames, passwords,
external identities, and owner-role assignments remain usable. Previously
stored email addresses remain in the data; this switch does not delete them.
They are not used for login, email features, or new owner grants while email
is disabled. Re-enabling email makes those addresses available again. A user
who previously signed in only by email must use their username. Use the
Operator CLI to find it.

External providers use identity subjects instead of email. In this mode,
Chatto ignores `request_email` and custom provider scopes, uses the provider's
basic identity scopes, and ignores email claims, including claims in pending
flows. Choose a provider that supports basic identity without an email scope.
Providers can still return an unsolicited email claim; Chatto does not save it
or use it for account creation.

## Run Chatto as a systemd Service

On Linux, use systemd to start Chatto and restart it after a failure. Create
this unit:

```ini
# /etc/systemd/system/chatto.service
[Unit]
Description=Chatto
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=chatto
Group=chatto
WorkingDirectory=/opt/chatto
ExecStart=/opt/chatto/chatto run -c chatto.toml
Restart=always
RestartSec=5
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target
```

Make sure that the `chatto` user can read `chatto.toml` and write the data
directory. Then, enable and start the service:

```bash
sudo systemctl enable --now chatto
```

<Aside type="tip">
  `AmbientCapabilities=CAP_NET_BIND_SERVICE` lets Chatto bind to ports below
  1024. Remove this line when Chatto listens only on ports that are 1024 or
  higher.
</Aside>

## Add Calls

The standalone binary does not include LiveKit. Select one of these methods to
add calls:

1. Use [Docker Compose](/guides/deployment/docker-compose/) with the included
   LiveKit service.
2. Run a separate [LiveKit
   server](https://docs.livekit.io/home/self-hosting/local/). Then, configure
   the LiveKit environment variables.
